# Deploy a Jykre Studio release

Jykre Studio is a desktop app, so "deploy" means **release**: a `v*` tag pushed
on `main` makes GitHub Actions build the Windows and Linux archives, sign them
with the release key and draft a GitHub Release. Nothing is hosted. The
maintainer signs (approves the signing stage) and publishes the draft.

The flow has two phases with one hand-off in the middle:

1. **Prepare**: bump, gate, commit, push, pull request. Then **stop** and ask the
   user to merge the pull request into `main`.
2. **Ship** (after the user says it is merged): tag `main`, push the tag, check
   that the release workflow started, give the user the link, and prepare the
   notes of the draft.

## How to behave

- **Do not ask at each step.** Say what you are going to do as a short list,
  then do it. Example:

  > Vou:
  > - commitar as alterações pendentes
  > - subir a versão para 0.4.0 e rodar `cargo xtask check --full`
  > - commitar o release e fazer o push de `release/0.4.0`
  > - abrir o pull request para `main`
  >
  > Depois paro e peço para você fazer o merge.

  Only list the steps that apply (no "commit pending changes" when the tree is
  clean). Reply in the user's language.
- **Stop and ask only when you cannot continue safely**: the target version is
  ambiguous, the tag already exists on `origin`, the gate fails, `Cargo.lock`
  would change a third-party crate, or a signing secret/key is the problem.
- Never force-push, rewrite pushed history, move or delete a pushed tag, push
  with `--tags`, or skip hooks (`--no-verify`).
- Never read, print, create or move `ZIPSIGN_PRIVATE_KEY`, `*.key` files or
  `assets/update/release-key.pub`. Signing happens only in CI.
- A release changes versions and documentation, not behavior. Do not add or
  upgrade dependencies, change the SQLite schema or a core contract as part of
  it.
- Never make the gate pass around a problem: no `#[allow(...)]` to silence a
  lint, no `#[ignore]` or deleted test, no weakened assertion.
- Report each check as **passed**, **failed** or **not run** with the reason.
  An unavailable tool (Docker, `gh`, `cargo deny`) is "not run", never a pass.

## Phase 1 — Prepare

### 1. Establish the facts

```bash
git status --short && git branch --show-current
git fetch --tags origin
gh release list --limit 5
git tag --sort=-v:refname | head -5
grep -n '^version' Cargo.toml          # [workspace.package] version
```

- **Target version `X.Y.Z`**: the one the user gave; otherwise the one in the
  branch name (`release/0.4.0`). If neither exists, ask. A tag for it must not
  exist locally or on `origin`.
- **Branch**: `release/X.Y.Z`. If you are on it, use it. If you are elsewhere
  (for example `main`), create it from the current HEAD.
- **Where am I?** The user may come back mid-flow. If `Cargo.toml` already has
  `X.Y.Z` and the release commit is on `main`, go to Phase 2. If the tag already
  exists, go to "Prepare the draft's notes".
- **Previous published release** `vPREV`: the latest non-draft release in
  `gh release list` (not merely the highest local tag).

Announce the plan (see "How to behave"), then continue.

### 2. Commit the pending changes

If `git status` is not clean, review `git diff` and commit the pending work
before the release commit, so the release commit contains only the release.
Group related changes; each commit message is a short imperative summary, a
blank line, then a plain-English bullet list of the user-visible changes.
Stage by file name, not `git add -A`; leave out anything that looks like a
secret, `.env` or local output.

### 3. Bump the version

| File | Change |
| --- | --- |
| `Cargo.toml` | `[workspace.package] version = "X.Y.Z"` (every crate uses `version.workspace = true`) |
| `Cargo.lock` | Regenerated by cargo; only the workspace crates may change |
| `README.md` | "Project status": latest release link `[vX.Y.Z](../../releases/tag/vX.Y.Z)` and a sentence on what the version adds; the `zipsign verify` examples that name archive files (`jykre-studio-vX.Y.Z-windows-x86_64.zip`, `…-linux-x86_64.tar.gz`); feature text that changed |

```bash
cargo update --workspace
git diff -U0 -- Cargo.lock | grep '^[-+]name\|^[-+]version' | head -60
```

If a third-party crate moved, undo that part: it is a dependency change.

Write README prose for users, in plain English, in the tone already there.
Take the changes from the commit history (see "Write the notes"), not from
guesses.

### 4. Run the gate

```bash
cargo xtask check --full
cargo build --release --locked --bin jykre
```

- `--full` is required for a release. It runs `cargo xtask check` (architecture
  check, `cargo fmt --check`, Clippy with `-D warnings`, `cargo test --workspace`
  with doctests), live PostgreSQL 14/18 and MySQL 8.4/9.7 tests in Docker, the
  benchmarks in quick mode and `cargo deny --locked check`.
- Run it in the background if it may take long, and read the real output. If
  Docker or `cargo-deny` is unavailable, run `cargo xtask check`, report `--full`
  as **not run (reason)** and say so in the hand-off message; do not call it a
  pass.
- For a release with UI changes, say whether the affected flows were looked at
  in the app. If not: "Visual check: not run".

### 5. Release commit, push and pull request

```text
Release X.Y.Z

- The workspace version is X.Y.Z. The README describes X.Y.Z: <what it adds>.
- <other user-visible change>
```

```bash
git add Cargo.toml Cargo.lock README.md      # plus any other file you changed for the release
git commit
git push -u origin release/X.Y.Z
gh pr list --head release/X.Y.Z --json url   # reuse the PR if one is open
gh pr create --base main --head release/X.Y.Z --title "Release X.Y.Z" --body-file <notes file>
```

The pre-commit hook runs `cargo fmt --all --check`; if it fails, fix the
formatting and make a **new** commit. Use the notes of the release (see "Write
the notes") as the pull request body. After opening the PR, call the ccd_pr
`get_status` tool and, if it does not report the PR, `bind_pr`. Do not poll CI.

### 6. Hand off to the user

**Do not tag.** End the turn with the PR link, the gate results, and a request:

> Faça o merge de #N em `main` e me avise. Depois eu crio a tag `vX.Y.Z` e
> disparo o release.

## Phase 2 — Ship (after the user says the PR is merged)

### 7. Tag `main` and push the tag

```bash
git fetch origin --tags
git checkout main && git pull --ff-only origin main
grep -n '^version' Cargo.toml                    # must be X.Y.Z
git tag --list vX.Y.Z; git ls-remote --tags origin vX.Y.Z   # both must be empty
git tag -a vX.Y.Z -m "Release X.Y.Z"
git push origin vX.Y.Z                           # only this tag
```

Stop if `main` does not contain the release (`Cargo.toml` is not `X.Y.Z`) or the
merge is not there yet: tell the user instead of tagging another commit.

### 8. Confirm the release workflow started; do not monitor it

```bash
gh run list --workflow release.yml --branch vX.Y.Z --limit 1 --json databaseId,status,url
```

If nothing is listed yet, wait a few seconds and check once more. If it is still
missing, say so and give `https://github.com/alandariva/jykre-studio/actions/workflows/release.yml`.
Do **not** use `gh run watch`, loops or timers.

Pipeline for reference: `windows` and `linux` (gate, `cargo build --release
--locked`, package) → `sign` (zipsign with `ZIPSIGN_PRIVATE_KEY`, environment
`release`, verified against the committed public key) → `verify-windows` →
`draft` (`gh release create --draft --generate-notes`). The archive names
(`jykre-studio-vX.Y.Z-<os>-x86_64.<ext>`) are part of the signature context.

Tell the user, with the run link:

> O release `vX.Y.Z` foi iniciado: <run link>. Quando a execução chegar à etapa
> de assinatura (`sign`), é com você assinar/aprovar. Me avise quando o draft
> existir que eu atualizo a descrição.

### 9. Prepare the draft's notes

The notes were written before the pull request (see below). Save them to a file
outside the repository (the session scratchpad or the system temp folder) and
show them to the user in the hand-off message so they can read them.

When the user says the draft exists:

```bash
id=$(gh api repos/alandariva/jykre-studio/releases --jq '.[] | select(.draft and .tag_name=="vX.Y.Z") | .id')
gh api -X PATCH repos/alandariva/jykre-studio/releases/$id -F body=@<notes file>
gh api repos/alandariva/jykre-studio/releases/$id --jq '{draft, tag_name, body}' | head -c 600
```

(`gh release edit vX.Y.Z --notes-file <file>` works too when it finds the draft.)
Leave the draft a draft. Never publish it, delete it or change its assets: the
maintainer publishes after signing and checking the Windows zip in Explorer and
7-Zip. A `-rc.N` release is marked Pre-release by the maintainer when
publishing.

If the notes file is gone (a new session), write the notes again the same way.

## Write the notes

Read the **title and description of every commit** since the previous published
release, and write the notes for users, not developers:

```bash
git log --no-merges --format='%h %s%n%b%n---' vPREV..HEAD
# vPREV is not an ancestor of HEAD (e.g. it was tagged on a side branch)? Drop what it already shipped:
git merge-base --is-ancestor vPREV HEAD || git log --no-merges --cherry-pick --right-only --format='%h %s%n%b%n---' vPREV...HEAD
```

Skip the "Release X.Y.Z" commit, merge commits and changes with no user-visible
effect (refactors, tests, internal docs) unless they matter to users.

Pattern of v0.3.0 and v0.3.1 (check `gh release view vPREV` for the exact tone):

```markdown
## Added

- **Feature name.** What it does for the user, in plain sentences. Keys in `code`, UI labels in **bold**. Limits and platform differences at the end

## Changed

- **Area.** What behaves differently now and how to use it

## Fixed

- Plain sentence on what no longer goes wrong, from the user's side

## Upgrading from PREV

Update from the app (**Restart now**), or download and extract this release. Connections, settings and saved queries are kept.

**Full Changelog**: https://github.com/alandariva/jykre-studio/compare/vPREV...vX.Y.Z
```

- Sections in this order: `Added`, `Changed`, `Fixed`; leave out the empty ones.
- **Added** and **Changed** bullets start with a bold lead-in ending in a
  period; **Fixed** bullets are plain sentences. No commit hashes, no
  `feat:`/`fix:` prefixes, no internal module names, no marketing language.
- A security fix names its advisory id (for example `SQLite 3.54.1 (RUSTSEC-…)`).
- If the release needs a manual step to upgrade (a migration the user must
  react to, a removed setting), say it under the upgrading section instead of
  the standard sentence.
- The same text serves as the pull request body and the draft's description.
