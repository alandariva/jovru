# Version 0.3.0

Date: November 8, 2026.

- **Approval:** Approved by the maintainer on 2026-11-08: the thesis
  (decision R: 0.3.0 ships SQL → script), the build order (straight through
  phases 1, 3, 4 and 5, interface last) and milestones A1–A7. Each ADR and
  dependency a milestone needs is still accepted on its own before that
  milestone is implemented.
- **Implementation:** Not started. The
  [SQL Job proof of concept](../automation-sql-job-poc.md) is complete.

Version 0.2.0 made the core reliable for daily use. Version 0.3.0 adds the
first automation: a saved SQL Job whose output feeds an external program,
run manually, stopped at any time, with a history that says what ran and how
it ended. The design is the
[automation engine specification](../automation-engine-specification.md),
version 1.2.

This document defines **milestones**, not how to achieve them. If a request
expands the scope beyond them, stop and ask the maintainer.

## Thesis

A user saves a SQL Job and an external program, chains them, runs the chain
by hand with typed inputs, and sees each step's state, cause and counters,
without a tab open for it and without a run ever being replayed.

## Outside this release

- Phase 6 of the specification: artifacts, `ask` and `confirm`, `db.query`
  from external programs
- Phase 7: schedules, cache, secret broker, HTTP, command palette, other
  transports, a published SDK
- Execution while the application is closed (excluded, Q-14)
- Parallel or conditional steps, retries, `native_flow`, a visual workflow
  editor, sandboxing
- Validating macOS (maintainer's decision, 2026-11-08). The
  specification's CA-12 asks for each platform; for 0.3.0 it applies to
  Windows and Linux only, as in 0.2.0
- Validating SQL Jobs against a Databricks workspace (Q-23): Databricks is
  covered by local HTTP tests and documented as not validated
- Importing and exporting jobs (Q-19)

## Milestones

A milestone is **complete** when its *Done when* criterion holds. They are
built in order; 0.3.0 ships when all are complete.

  ADR-0033 to ADR-0036 accepted; the proof of concept's live experiments
  passed under `--full`; [`process-wrap`](../process-supervision-dependency.md)
  approved; the phase 5 revision approved; Q-15…Q-32 answered. Proposed,
  awaiting approval: the phase 3 and 4 revisions (specification, sections
  9.1 and 9.2) and [ADR-0037](../../adr/0037-external-program-runs.md).

- **Done when:** [ADR-0033](../../adr/0033-automation-database-service-and-lock.md)

### A2 — Durable SQL Job (phase 1)

- **Done when:** CA-01, CA-02, CA-05, CA-11, CA-13 and CA-14 hold, with the
  phase 1 tests of the specification's section 11, on PostgreSQL, MySQL and
  SQLite; Databricks through its local HTTP tests, documented as not
  validated against a workspace (Q-23).

### A3 — External program (phase 3)

- **Done when:** CA-03 and CA-07 hold for a program started without a shell,
  with grandchildren killed on Stop and timeout after the 5 s request
  (Q-17), logs on disk within
  [ADR-0036](../../adr/0036-program-logs-on-disk.md), a changed program file
  blocking the run until it is published again (Q-16), and the trusted-code
  warning on first run (Q-10). Linux is validated here; Windows through a
  checklist the maintainer runs, its results recorded from the report
  (Q-24).

### A4 — `jjp/1` (phase 4)

- **Done when:** CA-04 and CA-07 hold; the token reaches the program through
  stdin only (Q-12) and is absent from the environment, logs and telemetry;
  a testable JavaScript example lives in `examples/` and no SDK is
  published (Q-13).

### A5 — SQL → script (phase 5)

- **Done when:** CA-09 holds for a SQL Job feeding an external program;
  declared outputs are persisted only for jobs that opt in, within
  ADR-0034's limits; cancellation and failure cascade; a global limit of 1
  still progresses.

### A6 — Automation interface (phase 2, widened)

- **Done when:** CA-15 holds for SQL Jobs, programs and chains: create,
  edit, run with the input form, stop, read the history and navigate with
  keyboard and focus; every rule in the specification's section 8.1.1
  (limits, queue, timeouts, `effect_unknown`, versions, the plan
  confirmation, persisted outputs, program logs, trusted code) is stated
  where it applies; Automation lives in the sidebar with tabs in the main
  area, the chain editor is a form and history is per job plus a global
  list (Q-20–Q-22); the budgets of the specification's section 8.2 hold
  and their numbers are reported; the flows are checked in the application
  on Linux and, through the maintainer's checklist, on Windows (Q-24).

### A7 — Documentation aligned with the code

- **Done when:** Architecture, Persistence, Security, Reliability, UX and
  Testing describe the automation as built; the specification and the proof
  of concept record what was implemented; the root README presents the
  feature and its limits (no sandbox, external code runs with the user's
  privileges).

## Branches and integration

- `release/0.3.0` was cut from `release/0.2.0` with the proof of concept and
  these documents (Q-32). Each milestone A2–A7 reaches it through a pull
  request of its own, with the gate passing (`--full` when the milestone
  touches drivers, execution contracts or dependencies).
- `release/0.2.0` is merged into `release/0.3.0` as it moves, and `main`
  once 0.2.0 ships.
- The MySQL `CALL` fix lands on `release/0.2.0` first, through its own pull
  request, and reaches 0.3.0 by that merge, before A5 (Q-30).
- Visual checks on Linux are tried on the development machine under `Xvfb`
  with software Vulkan; if the application does not run there, they join the
  maintainer's Windows checklist (Q-31).

## Boundaries applying to every milestone

- No schema, contract, dependency or ADR change beyond what an accepted ADR
  or an approved proposal allows.
- No input value, cell, scalar or server message is written anywhere except
  declared outputs under ADR-0034.
- A run is never replayed.
- `cargo xtask check --full` passes for every milestone that touches drivers,
  execution contracts or dependencies.
