# Version 0.3.0

Date: November 8, 2026.

- **Approval:** Approved by the maintainer on 2026-11-08: the thesis
  (decision R: 0.3.0 ships SQL → script), the build order (straight through
  phases 1, 3, 4 and 5, interface last) and milestones A1–A7. Each ADR and
  dependency a milestone needs is still accepted on its own before that
  milestone is implemented. Milestones A8–A15 (the SQL editor, the result
  grid, shortcuts and schedules) were added by the maintainer on
  2026-11-08; their specification, ADRs and dependencies are likewise
  accepted on their own before each is implemented.
- **Implementation:** A8–A15 not started. A1–A7 implemented on
  `feature/automation` (2026-11-08); waiting for the maintainer's review
  and the Windows
  [checklist](0.3.0-windows-checklist.md). A1 is complete; A2–A7 are
  implemented. `cargo xtask check --full` **passed** on Linux on the merged
  branch (commit `24267f9`): architecture, fmt, Clippy, the workspace tests,
  the live tests on PostgreSQL 14/18 and MySQL 8.4/9.7 (the automation ones
  included), the benchmarks in quick mode and `cargo deny`. **Not run:**
  anything on Windows, release-build performance measurements, and a
  Databricks workspace (Q-23).

Version 0.2.0 made the core reliable for daily use. Version 0.3.0 adds the
first automation: a saved SQL Job whose output feeds an external program,
run manually, stopped at any time, with a history that says what ran and how
it ended. The design is the
[automation engine specification](../automation-engine-specification.md),
version 1.2. Beside it, the release makes the SQL editor's search, replace
and multiple cursors known, adds going to a line, editing data in the
result grid, importing a CSV or Excel file into a table, shortcuts the user
chooses, schedules while the application is open, and hiding, reordering,
freezing and finding grid columns (A8–A15).

This document defines **milestones**, not how to achieve them. If a request
expands the scope beyond them, stop and ask the maintainer.

## Thesis

A user saves a SQL Job and an external program, chains them, runs the chain
by hand with typed inputs, and sees each step's state, cause and counters,
without a tab open for it and without a run ever being replayed.

## Outside this release

- Phase 6 of the specification: artifacts, `ask` and `confirm`, `db.query`
  from external programs
- Phase 7, except schedules while the application is open (A13): cache,
  secret broker, HTTP, command palette, other transports, a published SDK
- Execution while the application is closed (excluded, Q-14)
- Parallel or conditional steps, retries, `native_flow`, a visual workflow
  editor, sandboxing
- Validating macOS (maintainer's decision, 2026-11-08). The
  specification's CA-12 asks for each platform; for 0.3.0 it applies to
  Windows and Linux only, as in 0.2.0
- Validating SQL Jobs against a Databricks workspace (Q-23): Databricks is
  covered by local HTTP tests and documented as not validated
- Importing and exporting jobs (Q-19)

### A9 — Go to a line

- **Status:** Implemented, not yet checked in the application or measured.
  `Ctrl G` (the `GoToLine` action, in the SQL editor's key context; no key
  of `gpui-base` 0.9.0 uses it) opens a field over the editor that has the
  keyboard, in a query tab, a report panel or a SQL Job; `12` or `12:5`
  moves the cursor there with the editor's `set_cursor_position`, which
  scrolls it into view; a line past the text goes to the last one and the
  notice bar says so. What is typed and where it leads are read by
  `jykre::go_to_line` (unit tests); going reads only the rope's line index,
  so nothing is computed per frame or copied. Listed in User experience
  and **Preferences › Shortcuts** (English and pt-BR). The maintainer
  decided that this milestone includes marking MySQL and Databricks error
  positions: their drivers now read the position from the message
  (`position.rs` in each driver, unit tests on the servers' message shapes,
  a fixture test for a failed Databricks statement and a MySQL live test
  under `--full`), so the editor marks them as PostgreSQL's, and User
  experience's deviation is narrowed to what is still not marked. Left:
  the gate with `--full` (drivers changed), the frame measurement in a file
  above 256 KiB in a release build, and the check with the keyboard in the
  application on Linux and Windows.

- **Done when:** a shortcut, an action in the keymap that no editor key
  uses, asks for a line (and optionally a column) in the SQL editor that
  has the keyboard, moves the cursor there and scrolls it into view; a line
  beyond the text goes to the last one and says so; it stays within the
  frame budget in a file above 256 KiB
  ([Large `.sql` files](../editor-large-files.md)); it is listed in User
  experience and **Preferences › Shortcuts**, and checked with the keyboard
  in the application.
- **Open decision:** whether marking the position of a MySQL or Databricks
  error, which today they give only in the message (User experience,
  *Known deviations*), belongs to this milestone.

### A10 — Editing data in the result grid

- **Status:** Not started. The grid is read-only; the only SQL it
  generates is the copy as `INSERT`s. Version 0.2.0 left this out.
  [ADR-0039](../../adr/0039-editing-result-data-through-the-driver.md) is
  proposed (2026-11-08) and awaits the maintainer's approval, with the open
  decisions E-1 to E-7.

- **Done when:**
  - An ADR, accepted before implementation, says which results can be
    edited and how the driver tells it (the table each column comes from,
    a key that identifies each row), how changes are written and in which
    session and transaction, and what a driver that cannot tell does. A
    change to the driver contract is part of that ADR.
  - In a result the ADR deems editable, a cell can be changed or set to
    NULL, and rows inserted and deleted; any other result says why it is
    read-only.
  - Nothing is written without the user seeing what will be written and
    confirming it. Values are bound by the driver, never written into the
    SQL, and are not reinterpreted (exact numbers, NULL apart from the text
    `NULL`, temporal values without time zone conversion).
  - The tab's transaction is honoured: inside an open transaction the
    change stays uncommitted and the toolbar says so; outside one, a write
    that affects other rows than the ones edited is not committed silently.
    On a connection marked **Production** it asks first, as `jykre::guard`
    does.
  - Live tests on PostgreSQL, MySQL and SQLite under `--full`; the grid's
    keyboard and focus are checked in the application, and the result
    budgets of [Performance](../../standards/performance.md) still hold.
- **Open decisions:** whether an edit writes directly or generates the
  statements into the editor; whether pending edits are written together
  or one by one; whether Databricks is included.

### A11 — Importing a CSV or Excel file into a table

- **Status:** Not started. The application exports to CSV and XLSX but
  reads neither; no dependency in the workspace reads them. The
  [dependency proposal](../csv-and-xlsx-reading-dependencies.md) (`csv`,
  `calamine`, `encoding_rs`) and
  [ADR-0040](../../adr/0040-importing-files-into-a-table.md) were approved
  and accepted by the maintainer on 2026-11-08, with every recommendation of
  I-0 to I-5. Writing the rows reuses ADR-0039's write path, which is still
  proposed.

- **Done when:**
  - A dependency proposal for reading CSV and XLSX, per
    [Stack and dependencies](../../standards/stack-and-dependencies.md),
    is approved or rejected before implementation; a rejection is not
    answered by a hand-written reader that narrows the feature.
  - The user chooses the file (and the sheet of a workbook), the header
    row, the CSV's delimiter and encoding, and the table, maps the file's
    columns to the table's with a preview of the first rows, and runs it.
  - Values are bound by the driver, never written into the SQL, and
    converted by the database; text from a CSV reaches it as written. That
    an XLSX file stores numbers as floating point is said where it applies.
  - The import streams the file off the UI thread with bounded memory,
    shows progress after 300 ms and, past 2 s, its elapsed time and a way
    to cancel; it has a timeout. What a failure or a cancellation leaves in
    the table is said in words, and on a connection marked **Production**
    it asks first.
  - Live tests on PostgreSQL, MySQL and SQLite under `--full`, with
    dedicated synthetic files; the flow is checked in the application.
- **Open decisions:** whether the import is all or nothing or commits in
  batches; whether it may create the table; whether Databricks is
  included.

### A12 — Shortcuts the user chooses

- **Status:** Implemented, not yet checked in the application. The
  maintainer decided (2026-11-08) that the editor component's own keys can
  be changed too. The keymap's bindings at start are its defaults
  (`src/app/shortcuts.rs`); a change rebuilds it from them without the
  default bindings of the actions the user changed and with the chosen keys
  in the same contexts, so the editor component's actions are rebound
  without patching it (its keys that also move lists and menus,
  `ui::SelectUp` and the like, change only in text fields). The window's
  commands, the explorer's and the result grid's keys and moving a result
  tab became actions; what stays a raw handler is typing and moving inside
  one focused control and `Esc` closing a grid's or report panel's layer
  after the window's `Dismiss`, which the UI guidelines now name, and their
  deviation is closed. **Preferences › Shortcuts** records keys with the
  keyboard alone, names a collision (with **Take it**) before taking a key,
  and resets one action or all; a change applies at once and every place
  that names a key reads it from the keymap. The choices are kept in
  `keymap.shortcuts` ([Persistence](../../reference/persistence.md));
  what cannot be used is set back, said once and written again. The rules
  are `jykre::keymap`, with unit tests, and the application's defaults are
  tested for collisions. Left: the gate, and the check with the keyboard in
  the application on Linux and Windows.

- **Done when:**
  - Every shortcut of the application is a GPUI action in one keymap, and
    the UI guidelines' deviation about it is closed.
  - **Preferences › Shortcuts** changes an action's keys by pressing them,
    with the keyboard alone; a key another action or the editor uses is
    named before it is taken, and nothing is bound twice without saying so;
    each action, and all of them, can go back to the default.
  - A change applies at once, without a restart, and every place that names
    a shortcut (tooltips, menus, User experience's table where it says
    "the default") shows the key in use.
  - The choices are kept in `config.db`'s `settings`, documented in
    [Persistence](../../reference/persistence.md); a stored choice for an
    action that no longer exists, or that cannot be read, is ignored and
    said once, never a failure to start.
- **Open decision:** whether the editor component's own keys (A8's search
  and cursors, moving and selecting) can be changed too.

### A13 — Schedules while the application is open (phase 7)

- **Status:** Decisions closed, implementation not started. On 2026-11-08
  the maintainer approved the scheduling revision of the
  [specification](../automation-engine-specification.md#951-schedules-while-the-application-is-open-approved-revision)
  (sections 9.5.1–9.5.10), accepted
  [ADR-0041](../../adr/0041-schedules-and-grants.md) and approved the
  [`jiff` proposal](../schedule-time-zone-dependency.md). Q-33 and Q-36 to
  Q-40 follow the recommendations: a notification is opt-in per schedule
  through GPUI's existing API (Q-40 (c)). Q-34 and Q-35 changed: missed
  times (ignore, run once, or queue up to N) and overlap (skip, queue one,
  or allow concurrent runs) are policies chosen per schedule, under
  consent. **Implemented (2026-11-08), waiting for the gate (`--full`:
  the execution contracts and the schema changed), `cargo deny` and the
  check in the application:** migration 5, the scheduler
  (`src/automation/schedule/`) with engine tests on a manual clock, and the
  job tab's **Schedule** with the consent dialog, the indicator and the
  opt-in notification. Windows lines W-25 to W-28 of the
  [checklist](0.3.0-windows-checklist.md).

- **Done when:**
  - The specification's scheduling part of phase 7 is written and approved,
    as phase 5's was for A1, and the ADR for its tables in `automation.db`
    (`Schedule` and `Grant`, a new migration) is accepted before
    implementation; a dependency for the schedule's grammar, if one is
    needed, is proposed per
    [Stack and dependencies](../../standards/stack-and-dependencies.md).
  - A job or chain can be given a schedule (an interval or a calendar
    rule), turned off and removed; the Automation section shows each
    schedule's next run in the time zone it is defined in.
  - A schedule runs only while Jykre Studio is open, and in the instance
    that holds the automation lock; the documentation says plainly that
    nothing runs while it is closed (Q-14).
  - Consent is explicit, revocable and bound to the published version, the
    connection and its revision, the context and the environment; a manual
    confirmation is never promoted to it (section 7.2, P-15). A change to
    any of them suspends the schedule until it is confirmed again.
  - A scheduled run never opens a dialog: a password not remembered fails
    with `Authentication`, and a production confirmation is part of the
    consent. Overlap (a run still active at the next time) and times missed
    while the application was closed follow a rule the specification fixes;
    a run is never replayed.
  - Scheduled runs go through the same queue, limits and history as manual
    ones, with their cause recorded as the schedule; engine tests cover
    time zones, overlap, missed times and revocation, and the flow is
    checked in the application.
- **Open decision:** whether a scheduled run that ends badly tells the user
  beyond the history (a notification needs a dependency of its own).

### A14 — Hiding, reordering and freezing grid columns

- **Status:** Implemented (2026-11-08), waiting for the gate, the
  measurement and the visual check. The maintainer decided the open
  questions on 2026-11-08: the layout belongs to the result tab only, in
  memory, never saved; copying, exporting, the records view and the
  statistics follow the visible columns in display order. The layout is
  `jykre::column_layout::ColumnLayout`; the grid builds only the columns in
  view ([Results](../../reference/results.md#grid)). **Not run yet:** the
  gate, the sideways-scrolling frame measurement with many columns in a
  release build (`JYKRE_PROBE=1 cargo run --release --locked --
  --test-performance`, the 400-column size's `pan` phase,
  [Performance](../../standards/performance.md#how-to-measure)) and the
  check in the application with the mouse and the keyboard.

- **Done when:**
  - In every result grid (query tabs, report panels, a job's result), a
    column can be hidden and shown again, moved to another position and
    frozen at the left edge, with the mouse and from the keyboard (the
    header's menu).
  - How many columns are hidden is always visible, with a way to show them
    all; the values, their types and NULLs are untouched.
  - Scrolling sideways with frozen columns stays within the grid's budgets
    of [Performance](../../standards/performance.md), measured with a result
    of many columns, and the numbers are reported.
- **Open decisions:** whether the layout belongs to the result tab only or
  is remembered per table or query; whether copying, exporting, the
  records view and the statistics follow the visible columns and their
  order or the result's.

### A15 — Finding a column in the grid

- **Status:** Implemented (2026-11-08), waiting for the gate and the
  visual check. `Ctrl Shift F` (the `FindColumn` action) and the result
  toolbar's **Find a column** open the field; matching is
  `jykre::column_search`, ignoring case and accents. The maintainer decided
  on 2026-11-08 that the records view filters its lines with the same text
  ([Results](../../reference/results.md#grid)). **Not run yet:** the gate
  (its unit test keeps a search over 10,000 columns within a generous
  budget) and the check in the application with the keyboard alone.

- **Done when:**
  - A shortcut and a button in the result toolbar open a field that finds
    columns by name, ignoring case and accents, with the matching part
    marked (`MATCH_TEXT`, `MATCH_BG`) as other searches do.
  - Choosing a match scrolls the grid to the column and selects it; a match
    hidden by A14 says so and offers to show it.
  - It works with the keyboard alone, stays within the frame budget with
    thousands of columns (the list is computed when the text changes, never
    per frame), and is listed in User experience and **Preferences ›
    Shortcuts**.
- **Open decision:** whether the records view filters its lines with the
  same text.

## Boundaries applying to every milestone

- No schema, contract, dependency or ADR change beyond what an accepted ADR
  or an approved proposal allows.
- No input value, cell, scalar or server message is written anywhere on
  this computer (files, logs, telemetry) except declared outputs under
  ADR-0035. Writing to the user's database, as A10 and A11 do, is not
  covered by this rule.
- A run is never replayed.
- `cargo xtask check --full` passes for every milestone that touches drivers,
  execution contracts or dependencies.
