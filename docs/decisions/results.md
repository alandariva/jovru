# Decisions: Results

Why this area is built as it is. Each entry records what was decided, why, and which alternatives lost. The rules themselves are in [Results](../reference/results/README.md). Entries are numbered `D-NNNN`, and the numbers are stable.

<a id="d-0008"></a>
## D-0008: Compact result storage with a configurable row limit and a memory ceiling

*Accepted 2026-11-02 · implemented*

**Decision.** A result is one UTF-8 buffer for all cell text, a vector of cell end offsets and a NULL bitmap, with the column metadata stored once (`ResultData`, see [Model in memory](../reference/results/model.md#model-in-memory)). The row limit is per connection, up to 100,000; a memory ceiling per page (256 MB) stops reading even below it, and the footer says which limit applied ([Limits](../reference/results/model.md#limits)). The compact result is built, and driver cells dropped, on the Tokio runtime; a replaced result is dropped off the UI thread.
**Why.** A fixed 1,000-row limit was cheap with `Vec<Vec<String>>` plus a hash set of NULL positions, but one allocation per cell and a hash per NULL check do not scale, and the row count says little about memory: one wide text column outweighs many narrow ones, so the ceiling needs an exact figure. Measured: a 100,000 × 30 result takes about 38 MB (the old representation was estimated at about 102 MB). To tell a result with exactly the limit from one with more, the backend asks the driver for one row beyond the limit and discards it. The cost is that cells are read through an accessor instead of `&rows[r][c]`.
**Rejected.** Keeping `Vec<Vec<String>>`: one allocation per cell and no exact memory accounting, so it does not scale to 100,000 wide rows. Apache Arrow: columnar and fast but a large dependency for text cells. Spilling to disk: unlimited size, but results are never written to disk.

## D-0012: Result grid as its own cached entity

*Accepted 2026-11-02 · implemented · the page is shared as `Arc` since D-0022; the first validation below does not hold in GPUI 0.3.11*

**Decision.** The grid is a separate entity, `ResultGrid`, embedded in the workspace with `.cached(...)`; ownership, the calls between the two and the notification rules are in [Model in memory](../reference/results/model.md#model-in-memory). Grid behaviour (selection, copy, tooltips, `↵`, `name : type` headers, footer) did not change.
**Why.** GPUI keeps no retained element tree: a notified entity runs its `render()` again and lays out everything it returns. With the grid inside `Workspace`, hovering a cell, scrolling or selecting re-rendered the toolbar, editor and everything else, and every keystroke in the editor re-rendered the grid. After virtualization a release workspace frame cost about 2.5 ms, within budget, but a debug build spent about 11.5 ms of a 19 ms grid frame on the workspace alone, and the waste grows with every feature. The frame probe confirmed that typing in the editor no longer renders the grid (24 `Workspace` renders, 1 `ResultGrid`). The intended validation that hover, scroll and selection render only `ResultGrid` does not hold: GPUI marks every ancestor of a notified view dirty, so they still render `Workspace` ([Performance](../standards/performance.md#known-deviations), D-0013). There is no `set_sort`: the header sort lives inside the grid.
**Rejected.** Keeping the grid in `Workspace`: no refactor, but wasted work on the most used surface, growing with features. A separate entity without `.cached()`: still re-rendered whenever the workspace renders, losing half the benefit. One entity per row or cell: thousands of entities, events and handles for no gain, since `uniform_list` already limits rows to the visible ones.

## D-0022: Result pages shared across threads with `Arc`

*Accepted 2026-11-07 · implemented* · Amends D-0012 (the page is `Arc<ResultData>`, not `Rc<ResultData>`)

**Decision.** Result pages are shared as `Arc<ResultData>`; the rules for background work, release and `Weak` are in [Model in memory](../reference/results/model.md#model-in-memory). Everything else in D-0012 stands: one shared value, never copied, rendered only where visible.
**Why.** `Rc` cannot leave the UI thread, so anything that reads a whole page had to run there. Copying 500,000 cells built its text on the UI thread (about 85 ms), and an export has to write the pages the tab holds (up to 256 MB) before the rows the session still keeps open; on the UI thread that stalls the window for seconds, and copying the pages first costs tens of milliseconds and twice the memory. `ResultData` is plain owned data, already `Send` and `Sync`. The cost is an atomic operation per clone or drop, a few times per page shown, never per row or frame. Validation that stays: the grid, result tab and export tests assert the same things, the frame probe shows no change for scrolling, hovering and selecting at 100,000 rows, and exporting a multi-page tab keeps the UI thread under the stall budget (`stall_max_ms`).
**Rejected.** Keeping `Rc` and copying pages to the runtime in slices, one per frame: more view code, hundreds of frames for 256 MB and a second copy of each slice. Keeping `Rc` and copying a whole page before exporting: a memcpy of up to 256 MB on the UI thread and twice the memory. Converting to `Arc` only when an export starts: the conversion is the same copy.

## D-0024: Reports, with stored definitions, tabs of their own and a print HTML the user saves

*Accepted 2026-11-07 · implemented · Amended by D-0025: a report is a set of panels, each with its connection, SQL and chart, run on a session per connection and context*

**Decision.** Report definitions are stored under their own `reports` key of the `settings` table in `config.db` ([Persistence](../reference/persistence/README.md)), never results or typed values. A report opens in a tab of its own kind, a `ReportView` tracked in `AppView::report_tabs` apart from the SQL workspaces. Its result is not paged, charts are drawn by `gpui_kit` with floating point only for geometry, and the print HTML is written only where the user chooses ([Reports](../reference/results/reports.md#reports)).
**Why.** `WorkspaceState::to_value` writes back only the fields it knows, so a version that does not know a field erases it on its next save: reports inside `workspace.state` would be lost by an older version. A JSON value under its own key is how preferences and the workspace already live, so no migration was needed, and only the reports library writes it (half a second after changes settle and at quit; the demo writes nothing). Unknown keys are kept and written back; a value that cannot be read is reported and never written over. Query results never reach disk, so reports write no CSV file; copy reuses `cell_format::result_csv` and `copy_cells` with the confirmation above 50 MiB, and the print HTML is the one result on disk, where the user put it. A report run follows a SQL tab's flow (password prompt, production risk confirmation through `guard::risks`, `backend::query` with the parameters, superseded results dropped) and never runs in a SQL tab's session, so the values bound for its parameters stay in its own. Every place in `AppView` that assumed tabs are `Workspace`s (closing, moving, run shortcut, focus, catalogs, password prompt) gained a report branch. Report tabs are not reopened after a restart because that needs a new `workspace.state` field that older versions drop; recorded as technical debt.
**Rejected.** Reports inside `workspace.state`: one writer, but an older version would erase every report. A new `config.db` table: typed columns, but a migration for data that is always read whole. A report as a mode of the SQL tab: every SQL tab would carry form, chart and export state. Reopening report tabs now: deferred. A charting or PDF crate: a new dependency, fonts and layout code, while `gpui-component` already draws charts and browsers print to PDF. Print HTML in a temporary file opened at once: a result on disk where the user did not choose, and a file left behind.

## D-0025: Report panels, each with its connection, database, SQL and chart, run on a session per connection and context

*Accepted 2026-11-07 · implemented* · Amends D-0024 (a report is a set of panels; the stored format) and, for report tabs, D-0014 (a session per connection and context used, not one per tab)

**Decision.** A report holds up to 12 panels, each with its own connection, context, SQL, display and width, sharing the report's parameters ([Reports](../reference/results/reports.md#reports)). A report keeps one session per connection and context its panels use, at most four panels run at once and four idle sessions are kept, and the scheduling decisions live in `jovru::reports::run` ([Architecture](../reference/architecture.md#run-a-report)). The `reports` setting is at `"version": 3`. The `Driver` contract gains `session_connection(connection, context)`, the connection a session opens with so that names resolve in `context` from its first statement; the default returns the connection unchanged, and PostgreSQL returns the same connection with another database only when the profile offers `allDatabases`, otherwise a validation error.
**Why.** Users build reports that put revenue by region next to the costs of the quarter, or an archive database on another server beside the live one. A session applies a requested context only when it differs from the one it last applied, so a shared session would leave a "session default" panel in whatever database the previous panel used; a PostgreSQL session is bound to the database it connected to and cannot change it; and one session cannot span connections. A session per panel would open up to 12 connections (or execution contexts on a classic Databricks cluster). A run is always settled: after each panel the session is asked its context and transaction even when the result has more rows, so a `USE` in one panel's SQL cannot leak into the next. The least recently used idle session closes first; a connection whose settings change, or that is removed, stops its panels and closes its sessions (a new password keeps them). A run may ask for several passwords, one connection after another, and a panel whose connection cannot run fails alone. The tab group was first one per report, named after it; it became the shared **Reports** group on 2026-11-11 at the maintainer's request, which offers no new tab and goes away with its last tab ([User experience](../reference/ux/README.md)). Versions 1 and 2 of the stored format were never released; they are read as one panel (the report-level connection given to each) and written back as version 3.
**Rejected.** One connection per report: one password and check, but no archive server beside the live one. One session per report tab switching context before each panel (D-0014 as it stood): panels in sequence, inherited databases, no other database or connection. One session per panel: too many sessions. All report tabs in one group (first rejected in favour of a group per report, then adopted on 2026-11-11). A dashboard of independent saved queries: no shared parameters and a second library of layouts. Inferring the PostgreSQL database switch in the application: `match` on the driver kind outside the drivers (golden rule 3).

## D-0039: Editing result data through the driver, which reports each column's source and the row key

*Accepted 2026-11-08 · implemented · MySQL casts for unsigned integers, decimals and `DATE` amended the same day after live tests showed the declared casts adjusting values without a warning*

**Decision.** The driver, not the application, says which table each result column comes from (`ColumnInfo::origin`) and which key identifies a row (`Session::edit_target`); `Session::write` writes the changes atomically and `Session::write_script` generates statements for Databricks. All three have defaults that keep today's behaviour, behind `DriverCapabilities::row_writes`; the contract and each driver's catalog queries are in [Drivers](../reference/drivers/editing-and-import.md#editing-results), the rules and behaviour in [Editing](../reference/results/editing.md#editing).
**Why.** Origins come from what the protocol said when the statement was prepared, with no extra I/O: PostgreSQL's relation OID and attribute number, MySQL's and SQLite's `Column::origin()` (exposed by the pinned SQLx fork, D-0030). The catalog is read only when the user starts editing, so runs cost nothing, and through the tab's own session, which sees what its open transaction created and keeps the tab's transaction honoured, with a savepoint when one is open. Values are bound and converted by the server so nothing passes through a client type (golden rule 9). Maintainer decisions of 2026-11-08: E-1 write directly on PostgreSQL, MySQL and SQLite; E-2 pending edits written together; E-3 Databricks generates statements into a new query tab from a table inferred from the SQL text, a deliberate narrow exception living in its driver (golden rule 3) because its protocol reports no origin; E-4 the primary key, else a unique index on NOT NULL columns; E-5 key only, last write wins; E-6 MySQL and SQLite `schema.table` split at its only dot, several dots checked against the catalog, read-only unless exactly one split exists, so a name is never misattributed; E-7 10,000 changes per write. The write module is in `jovru-core` so every driver writes the same statement shapes, and D-0040 reuses the path for imports. SQLite names the base table even through a view, so a view written there goes to its table and the confirmation names it.
**Rejected.** Guessing the table from the SQL text: wrong for aliases, joins, views, CTEs and `search_path`, and SQL parsing in the application (golden rule 3), except for Databricks. The metadata cache for keys: may be stale and misses what the transaction created. Resolving the source on every run: a catalog query per `SELECT` and a PostgreSQL snapshot taken in a transaction. SQLx's `ColumnOrigin` text for PostgreSQL: `regclass::text` depends on `search_path`. MySQL keys from column flags: `flags` is private and marks columns, not which index. Writing in a new session: would not see the rows the transaction changed. Comparing every read column in `WHERE`: types without equality (`json`, `xml`, `point`) and approximate numbers could never be written. Widening the SQLx fork to expose schema and table separately (E-6 b): a dependency change under D-0030. Writing cell by cell on leaving it (E-2 b): a confirmation per cell or none, and half a correction committed on failure. Databricks read-only, or warehouses only with user-named keys (E-3 a/b): no transaction, informational keys and no binding on classic clusters, accepted instead as generated statements with that stated in the tab's header comment. The `rowid` as a key (E-4 c): can come later. No limit or 1,000 per write (E-7).
