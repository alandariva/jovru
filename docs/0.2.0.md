# Versão 0.2.0

Data: 6 de novembro de 2026.

A 0.1.0 entrega o núcleo do produto no Windows (conexões, SQL, grade,
relatórios, assistente, telemetria). A 0.2.0 é a versão em que esse núcleo
fica **confiável para uso diário**: o estado da sessão é honesto, a janela não
congela em operações grandes, o trabalho longo se cancela de verdade, a
aplicação tem ícone próprio, o Linux está validado, e a documentação descreve
o que o código faz.

Este documento define **marcos**. Não descreve como alcançá-los.

Se um pedido alargar o escopo além destes marcos, parar e perguntar ao
mantenedor.

## Tese

Uso diário sem surpresas no Windows, com Linux validado e ícone do produto.
Não é capacidade nova nem validação de macOS.

## Fora desta versão

Estes itens **não** são marco da 0.2.0:

- macOS validado
- Restaurar abas de relatório após o reinício
- Editor SQL mais rico (incluindo tree-sitter)
- Ferramentas ao vivo do assistente contra o servidor
- Outro driver
- Edição de dados na grade
- Splitter de SQL no driver
- Command palette virtualizada
- Retries automáticos de leitura
- TD-002 (bind de `:name` sem snapshot no PostgreSQL)
- Ancestrais finos da grade (ADR-0013), salvo se o checklist de resultados
  falhar no frame probe

## Marcos

Cada marco está **concluído** quando o critério *Done when* vale. A ordem
abaixo é a ordem em que os marcos se fecham; um marco posterior não substitui
um anterior incompleto.

### M1 — Transações honestas

O usuário vê se a sessão da aba tem transação aberta, alterações pendentes ou
transação falha, e a aplicação não reverte nem confirma trabalho em silêncio.

- **Done when:** o estado exibido bate com o estado real da sessão nos
  drivers que o protocolo permite ler; o que ainda for aproximação está
  nomeado em [technical-debt.md](technical-debt.md) e no README, sem
  prometer o que o código não garante. O teste live de `BEGIN` seguido de
  `SET TRANSACTION ISOLATION LEVEL` continua passando.

Referência: [TD-001](technical-debt.md#td-001--transaction-state-is-not-read-from-the-protocol).

### M2 — Cópia que não congela a janela

Copiar uma seleção ou a página como CSV (ou outro formato do menu) acima do
limite de confirmação não segura a thread da UI pelo tempo da geração do
texto.

- **Done when:** a confirmação acima de 50 MiB permanece; a geração do texto
  corre fora da thread da UI, com cancelamento e progresso quando passar do
  orçamento de cópia em [performance.md](performance.md); o desvio em
  [results.md](results.md) e o N031 em
  [pendencias-comportamental.md](pendencias-comportamental.md) estão fechados
  ou atualizados com o que ainda faltar de fato.

### M3 — Trabalho longo e feedback previsíveis

O dia a dia no Windows cobre cancelamento, formatação, filtro, TLS e busca
curta sem os desvios que hoje atrapalham.

- **Done when:**
  - existe um atalho próprio para cancelar um run (além do botão Stop e da
    confirmação ao repetir o atalho de executar)
  - Format mostra tempo depois de 2 s e pode ser cancelado
  - o filtro da grade não reconstrói a view a cada tecla; o rebuild cabe no
    orçamento de [performance.md](performance.md) em 100 mil linhas
  - a conexão ativa mostra se a sessão está cifrada e avisa se for texto puro
  - a busca de metadados com 1 ou 2 caracteres respeita o orçamento de
    [performance.md](performance.md), ou deixa claro que está a procurar
    fora da UI

### M4 — Ícone do aplicativo

A janela e o artefato instalável ou executável identificam o Jykre Studio
pelo ícone do produto, não pelo ícone genérico do runtime.

- **Done when:** o ícone aparece na janela principal e no executável
  publicado da 0.2.0 nas plataformas desta versão; o README ou o asset do
  repositório deixa claro qual é o ícone oficial.

### M5 — Validação no Linux

O núcleo da 0.2.0 roda no Linux com a mesma confiança que no Windows para os
fluxos críticos desta versão.

- **Done when:**
  - a aplicação sobe no Linux com as dependências de sistema do GPUI
    documentadas
  - os fluxos críticos de M1–M4 foram conferidos na UI no Linux (conectar,
    executar SQL, grade, cancelar, cópia, ícone)
  - o README deixa de dizer que só o Windows está validado: Windows continua
    como plataforma principal; Linux consta como validado na 0.2.0
  - falhas específicas do Linux encontradas nessa validação estão corrigidas
    ou registradas como desvio conhecido com severidade

### M6 — Documentação alinhada ao código

O que a 0.1.0 e a 0.2.0 entregam está descrito como entregue; o que ainda é
dívida está descrito como dívida.

- **Done when:**
  - os ADRs cujo código já cumpre a decisão estão **Accepted** (só o
    mantenedor muda o status)
  - as tabelas *Known deviations* dos documentos afetados refletem o código
    após M1–M5
  - [pendencias-comportamental.md](pendencias-comportamental.md) está
    sincronizado com o HEAD (N031 e menções obsoletas)
  - o README descreve a 0.2.0 (deixa de apresentar o produto só como
    protótipo 0.1.0)

### M7 — Aceitação e release

A versão sai com evidência, não só com diff.

- **Done when:**
  - o checklist de [results.md](results.md) foi percorrido na aplicação no
    Windows e no Linux
  - os fluxos críticos de M1–M5 foram conferidos na UI (teclado e foco onde
    couber)
  - `cargo xtask check --full` passou; se a versão trouxe mudança de
    dependência, `cargo deny --locked check` também
  - a versão do workspace é `0.2.0`
  - existe a tag `v0.2.0` e o GitHub Release correspondente
    ([workflow.md](workflow.md))

A 0.1.0 nunca foi tagueada: o mantenedor decide se tagueia 0.1.0 antes ou se
a 0.2.0 é o primeiro artefato público. Isso não bloqueia M1–M6.

## Limites que valem para todos os marcos

- Sem mudança de schema SQLite neste recorte, salvo aprovação explícita.
- Sem dependência nova ou `[patch]` sem aprovação do mantenedor
  ([stack-and-dependencies.md](stack-and-dependencies.md)).
- Contratos de driver, schema e ADR só mudam com aprovação e documento
  atualizado junto.
